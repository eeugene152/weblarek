# Интернет-магазин «Web-Larёk»

«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component

Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`

#### Класс Api

Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter

Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` - хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

### Типы приложения

В приложении используются следующие типы:

#### Тип TPayment

Тип описывает варианты, из которых покупатель может сделать выбор, как будет оплачивать товар.

- `card` - выбор оплаты картой;

#### Тип FormErrors

Объект, содержащий описания ошибок валидации форм. Ключи объекта соответствуют полям формы,
а значения — тексту ошибки. Если поле заполнено верно, ключ в объекте отсутствует.

- `payment?: string` - ошибка в поле payment;
- `address?: string` - ошибка в поле address;
- `email?: string` - ошибка в поле email;
- `phone?: string` - ошибка в поле phone;

### Интерфейсы приложения

В приложении используются две основные сущности для работы с данными: товар и покупатель.

#### Интерфейс "товар" - IProduct

Интерфейс описывает структуру данных отдельного товара (карточка товара), которые получаются с сервера.

- `id: string` - уникальный идентификатор товара;
- `title: string` - название товара;
- `image: string` - картинка с изображением товара;
- `category: string` - категория, к которой принадлежит товар;
- `price: number | null` - цена товара. как вариант - она можети отсутствовать;
- `description: string` - описание товара;

#### Интерфейс "покупатель" - ICustomer

Интерфейс описывает структуру данных покупателя (пользователя магазина).

- `payment: TPayment` - предлагает выбор вариантов оплаты через тип `TPayment`. пока не выбрано - значение отсутствует;
- `email: string` - поле для хранения электронной почты покупателя;
- `phone: string` - поле для хранения номера телефона покупателя;
- `address: string` - поле для хранения адреса покупателя;

В приложении используются следующие классы:

Поля класса:

`getSelectedProduct(id: string): IProduct | Undefined` - получить карточку выбранного товара по его `id`;
`setPreview(product: IProduct): void` — сохраняет товар, выбранный для подробного отображения;

Отвечает за хранение товаров, которые пользователь выбрал для покупки, и расчет стоимости.

`getProducts(): IProduct[]` - получение массива товаров в корзине;

`countBinProducts(): number` - получить количество товаров в корзине;

Отвечает за хранение данных клиента, выбор вариантов оплаты и проверку этих данных.
Поля класса:

### Изменения в моделях данных:

Все модели данных теперь принимают в конструктор брокер событий `events: IEvents`. Они полностью изолированы от отображения, но при любом изменении своих полей автоматически уведомляют приложение через генерацию событий в EventBus.

#### Класс `CatalogMain`

- Метод `saveProducts` после сохранения данных генерирует событие `items:changed`.
- Метод `setPreview` генерирует событие `preview:changed`.

#### Класс `BinData`

- Методы `addProduct`, `deleteProduct` и `clearBin` при любом изменении состава корзины генерируют единое событие `basket:changed`. Геттеры стоимости и количества при этом остаются "тихими" и события не эмитят, чтобы избежать бесконечных циклов.

#### Класс `CustomerData`

- Метод `setCustomerData` анализирует пришедшие частичные данные, обновляет поля и в самом коде (в самом конце метода) генерирует одно общее событие `customer:changed`.
- Метод `clearCustomerData` сбрасывает все поля и также генерирует событие `customer:changed`.

## Слой представления (View)

Все классы этого слоя отвечают за отображение интерфейса на странице, поиск HTML-элементов и обработку кликов.
Они **ничего не знают про сервер и про то, как устроены модели данных**. Они просто берут готовый объект с данными, раскидывают его по инпутам/текстам и выводят пользователю.

Все компоненты этого слоя наследуются от базового класса `Component`, который управляет DOM-элементами.

### Базовые компоненты инфраструктуры:

#### Класс `Header`

— управляет шапкой сайта. Находит иконку корзины и вешает на неё слушатель клика для открытия модального окна (`basket:open`). Принимает через сеттер `counter` количество товаров в корзине и динамически обновляет цифру на счетчике.

#### Класс `Gallery`

— сетка для каталога на главной. Просто принимает массив уже готовых сверстанных карточек и раскладывает их на экране.

#### Класс `Modal`

— универсальная «коробка» для модальных окон. Находит крестик закрытия и оверлей. Умеет сама открываться/закрываться и очищать контент, чтобы не захламлять память. Защищена от закрытия при случайном клике по центру окна (`stopPropagation`).

#### Класс `Success`

— финальное окно успешного завершения покупки. Находит кнопку закрытия «За новыми покупками!» и текстовое поле для вывода итогов. Принимает списанную сумму заказа из презентера и динамически выводит её пользователю через сеттер `total`.

### Семейство карточек товара (Наследуются от абстрактного класса `Card`):

#### Абстрактный класс `Card`

— общая база для всех карточек. Находит и умеет отрисовывать только два общих поля: название товара и его цену (учитывает цену `null` как "Бесценно").

#### Класс `CardCatalog`

— карточка товара для главной страницы. Дополнительно находит картинку и тег категории. Ловит клик по всей карточке через переданный колбэк (`actions`).

#### Класс `CardPreview`

— карточка детального просмотра в модалке. Находит описание товара и кнопку «Купить/Удалить». Если у товара нет цены — сама блокирует кнопку и пишет «Недоступно».

#### Класс `CardBasket`

— карточка товара внутри корзины. Вместо картинок находит и выводит порядковый номер (индекс) строки и кнопку удаления (иконку-корзинку).

##### Динамическое переключение цветов категорий (`CardCatalog` и `CardPreview`)

- Внутри сеттера `category` реализована автоматическая покраска фона тега. Класс не использует громоздкие `if/else`, а с помощью цикла перебирает карту констант `categoryMap` и через метод `classList.toggle` динамически навешивает нужный CSS-класс модификатора (например, `card__category_soft`), соответствующий пришедшему с бэкенда тексту.

### Семейство форм (Наследуются от базового класса `Form`):

#### Базовый класс `Form`

— общая база для всех форм. Отвечает за блокировку кнопки отправки, если форма невалидна, и вывод текста ошибок. Самое главное — он через событие `input` автоматически следит за каждым инпутом и сообщает в презентер, какое именно поле изменилось.

— форма первого шага заказа. Находит инпут адреса и две кнопки выбора оплаты ("Картой" / "Наличными"). Умеет красиво переключать класс активности кнопок через `classList`.

#### Класс `FormContacts`

— форма второго шага заказа. Самая простая — находит и обновляет только два текстовых инпута: email и телефон.

## Слой презентера (Presenter)

Презентер выступает в роли диспетчера - связывает слои данных (Models) и отображения (Views) между собой с помощью системы событий.

### Архитектурный подход и обоснование выбора

В соответствии с техническим заданием, для реализации Презентера был выбран **стандартный подход — размещение логики взаимодействия непосредственно в главном скрипте приложения `src/main.ts`**, без вынесения в отдельный изолированный класс.

**Обоснование выбора:**

1. **Соответствие масштабу приложения (Принцип KISS):** Приложение является одностраничным (Single Page Application) с фиксированным набором форм и окон. Создание дополнительного абстрактного класса-обертки привело бы к усложнению архитектуры (оверхеду) без реальной практической выгоды.
2. **Централизация логики:** Файл `main.ts` собирает в себе инициализацию всех моделей и компонентов инфраструктуры, становясь единой точкой сборки приложения, что упрощает отладку и чтение кода.

### Принцип работы:

- Презентер инициализирует брокер событий (`EventEmitter`), все необходимые модели данных и глобальные компоненты представления.
- Он настраивает подписки на события в EventBus (`events.on(...)`).
- Презентер строго следует паттерну MVP: он **не хранит внутри себя состояние и не меняет разметку напрямую**. Отрисовка интерфейса (ререндер) происходит исключительно в ответ на сигналы об изменении данных от моделей (например, `basket:changed`, `items:changed`) или при действиях пользователя в модальных окнах.

Благодаря этому подходу соблюдается инверсия зависимостей: компоненты отображения и модели абсолютно ничего не знают друг о друге, а вся связанность между ними изолирована внутри Презентера.

#### Спринт 1(TS8): Бизнес-логика и данные (Model)

1. **Спроектировал структуру данных:** Разобрал техническое задание и выделил основные сущности магазина — сам Товар, Корзину для покупок и Личные данные покупателя.
2. **Создал строгие правила (Типизацию):** С помощью TypeScript описал интерфейсы для всех сущностей, что защитило код от случайных ошибок (например, если сервер пришлет пустую цену или вместо текста придет число).
3. **Написал независимые Модели данных:** Создал три класса-модели (`CatalogMain`, `BinData`, `CustomerData`). Они умеют хранить данные, считать сумму корзины, удалять/добавлять товары и проверять правильность заполнения форм. Эти классы были полностью изолированы от верстки и отображения.
4. **Настроил связь с сервером (Слой коммуникации):** Написал класс `AppApi`, который умеет запрашивать реальный список товаров с сервера и отправлять готовый заказ обратно.

#### Спринт 2(TS9): Интерфейс и интеграция (View & Presenter)

5. **Разработал компоненты отображения (View):** Использовал готовый (в рамках проекта) базовый абстрактный класс `Component` для безопасной работы с DOM-деревом - построил на его основе разветвленную иерархию элементов:
   - Универсальное модальное окно (`Modal`).
   - Семейство карточек товара (`CardCatalog` для витрины, `CardPreview` для детального осмотра, `CardBasket` для списка в корзине).
   - Семейство пошаговых форм заказа (`FormOrder` для адреса/оплаты и `FormContacts` для телефона/email).
6. **Внедрил событийно-ориентированный подход (Event-Driven):** Связал все компоненты через единый брокер событий (`EventEmitter`). Доработал модели данных из первого спринта так, чтобы они автоматически генерировали события при любом изменении своего внутреннего состояния (например, `basket:changed`, `customer:changed`), обеспечивая реактивность интерфейса.
7. **Реализовал сложные интерфейсные фичи:**
   - Настроил динамическое переключение CSS-классов фона категорий товаров через циклы и метод `classList.toggle` на основе карты констант.
   - Написал логику автоматической блокировки/разблокировки кнопок покупки для товаров с ценой `null` ("Бесценно").
   - Спроектировал механизм валидации форм «на лету» (на каждый ввод символа в инпут) с фильтрацией вывода ошибок под конкретный шаг заказа.
   - Обеспечил сохранение и восстановление ранее введенных пользователем данных в инпутах и кнопках при случайном закрытии и повторном открытии модальных окон.
8. **Собрал Презентер приложения (`main.ts`):** Написал центральный управляющий слой приложения, который слушает события от интерфейса, передает команды в модели данных, обрабатывает асинхронные цепочки сетевых запросов (через `Promise`) и координирует своевременный рендер страниц. Настроил резервный механизм: при недоступности сервера приложение можно переключить на локальные моковые данные, сохраняя полную работоспособность.


## Работа над ошибками (Проведённый рефакторинг)

#### №1

После код-ревью с преподавателем проект был серьёзно перебран и доведён до ума. Вот список главных замечаний, которые мы нашли и исправили:

1. **Починил утечку памяти (Переиспользование окон):** 
   Раньше при каждом клике на «Купить» или «Корзину» приложение заново копировало HTML-шаблоны и создавало новые тяжелые объекты в памяти. Теперь все крупные окна (Превью, Корзина, Формы) создаются строго ОДИН раз при старте сайта. В обработчиках мы их больше не пересоздаём, а просто наполняем свежими данными.

2. **Избавился от «грязных» приведений типов (`as Promise`):**
   В сетевом коде `AppApi` раньше стояло насильное приведение типов через `as`, чтобы TypeScript не ругался. Заменил это на нормальные, «умные» дженерики (универсальные типы), которые заложены в базовый класс `Api`. Код стал короче и чище.

3. **Убрал пустой строку варианта оплаты:**
   Изначально, если оплата не была выбрана, в систему записывалась пустая строка `""`. Это логический косяк. Перевели этот статус на честный и понятный `null`. Заодно убрал из кода формы кучу условий `if/else`, заменив их на встроенный метод `classList.toggle` — теперь кнопки оплаты гаснут и загораются автоматически всего в две строчки кода.

4. **Защитил карточки от лишних данных:**
   Раньше при отрисовке карточек мы разворачивали в них весь объект товара (`...product`). Из-за этого внутрь верстки просачивались лишние данные (например, `id` или `description`), для которых в классах даже не было сеттеров. Теперь в метод `render` передаются только строго нужные поля, перечисленные вручную.

5. **Оживил картинки (`CDN_URL`):**
   Раньше на карточках не отображались картинки товаров, потому что сервер присылал короткие относительные пути. Подключил константу адреса картинок и теперь презентер сам склеивает правильную ссылку перед выводом на экран.

6. **Сделал события -> чистыми сигналами:**
   Раньше модели данных при кликах передавали вместе с событием тяжелые объекты (payload), что по MVP избыточно. Теперь события работают как простые сигналы - "что-то поменялось", а презентер сам идёт и берёт из модели свежие данные через геттеры.

#### №2

7. **Доделан синглтон для окна Успеха (`Success`):**
   Единственное окно, которое забыл перевести на переиспользование в прошлый раз. Оно продолжало клонировать шаблон при каждом заказе, а TS в коде ругался на неиспользованную глобальную переменную. Теперь оно тоже создаётся один раз на старте, а в `.then` и `.catch` мы просто передаём в него итоговую сумму.

8. **Изменен тайминг запуска моделей:**
    На старте приложения вызывалась очистка корзины `clearBin()` до того, как в коде регистрировались слушатели событий (`events.on`). В итоге стартовый сигнал модели улетал в пустоту, корзина не рендерилась пустой, а кнопка 'оформить' оставалась активной из шаблона. Перенес сброс моделей в  конец файла `main.ts`.

9. **Ненужные сигналы из Презентера:**
    До правки при открытии форм заказа мы вызывали `events.emit('customer:changed')` прямо из презентера, что неверно, т.к. это работа модели. Убрал этот код. Теперь формы один раз наполняются при стартовом сбросе моделей в конце файла, а дальше живут в памяти, сохраняя введённый текст в инпутах.

10. **Обработчик инпута адреса:**
    Логическая проблема: в условии проверки инпута у нас стояло `|| orderFormView`. Так как эта форма теперь синглтон и существует в памяти всегда, условие всегда превращалось в `true`, а ветка `else` не работатала никогда. Теперь запись значения идет напрямую в модель.

11. **Перевел все View на прямую работу с EventBus:**
    Ранее для Корзины и Превью использовались прослойки с колбэками (`onBuy`, `onOrder`). Теперь компоненты принимают брокер событий `events` в конструктор и сами генерируют сигналы в Презентер. 

12. **Заблокировал базовую форму от случайного создания:**
    Сделал класс `Form` строго абстрактным (`abstract class Form`). Теперь будет невозможно случайно создать пустую «сырую» форму через `new Form()`, ломая приложение.

13. **Альтернативный текст к картинкам карточек:**
    Переписал сеттеры картинок в карточках: теперь они принимают объект со ссылкой `src` и альтернативным текстом `alt`.
