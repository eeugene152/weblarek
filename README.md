# Интернет-магазин «Web-Larёk»
«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и  отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component
Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`


#### Класс Api
Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter
Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` -  хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные

### Типы приложения
В приложении используются следующие типы:

#### Тип TPayment
Тип описывает варианты, из которых покупатель может сделать выбор, как будет оплачивать товар.
- `card` - выбор оплаты картой;
- `cash` - выбор оплаты наличными;
- `` - пока не сделан выбор между первым и вторым вариантом;

#### Тип FormErrors
Объект, содержащий описания ошибок валидации форм. Ключи объекта соответствуют полям формы,
а значения — тексту ошибки. Если поле заполнено верно, ключ в объекте отсутствует.
- `payment?: string` - ошибка в поле payment;
- `address?: string` - ошибка в поле address;
- `email?: string` - ошибка в поле email;
- `phone?: string` - ошибка в поле phone;

### Интерфейсы приложения
В приложении используются две основные сущности для работы с данными: товар и покупатель.

#### Интерфейс "товар" - IProduct
Интерфейс описывает структуру данных отдельного товара (карточка товара), которые получаются с сервера.
- `id: string` - уникальный идентификатор товара;
- `title: string` - название товара;
- `image: string` - картинка с изображением товара;
- `category: string` - категория, к которой принадлежит товар;
- `price: number | null` - цена товара. как вариант - она можети отсутствовать;
- `description: string` - описание товара;

#### Интерфейс "покупатель" - ICustomer
Интерфейс описывает структуру данных покупателя (пользователя магазина).
- `payment: TPayment` - предлагает выбор вариантов оплаты через тип `TPayment`. пока не выбрано - значение отсутствует;
- `email: string` - поле для хранения электронной почты покупателя;
- `phone: string` - поле для хранения номера телефона покупателя;
- `address: string` - поле для хранения адреса покупателя;


### Классы приложения (модели данных)
В приложении используются следующие классы:

#### Класс "Каталог на главной" - CatalogMain
Отвечает за формирование основного каталога товаров, предпросмотр выбранного товара.

Поля класса:  
- `_products: IProduct[]` — хранит массив всех товаров;
- `_preview: IProduct | null` - хранит товар, выбранный для подробного отображения;

Методы класса:  
`saveProducts(products: IProduct[]): void` - сохраняет массив товаров, полученный от сервера, в модель;
`getProducts(): IProduct[]` - получение всего списка товаров. на входе параметров нет. возвращает список товаров;  
`getSelectedProduct(id: string): IProduct | Undefined` - получить карточку выбранного товара по его `id`;
`setPreview(product: IProduct): void` — сохраняет товар, выбранный для подробного отображения;
`getPreview(): IProduct | null` — возвращает товар, который сейчас находится в предпросмотре;


#### Класс "Корзина с товарами" - BinData
Отвечает за хранение товаров, которые пользователь выбрал для покупки, и расчет стоимости.

Поля класса:  
- `_products: IProduct[]` — массив товаров в корзине;

Методы класса:  
`getProducts(): IProduct[]` - получение массива товаров в корзине;
`addProduct(product: IProduct): void` - добавить продукт в массив корзины;
`deleteProduct(id: string): void` - удалить товар из массива корзины;
`clearBin(): void` — полностью очищает корзину (удаляет все товары);
`getBinProductsCost(): number` - получить сумму стоимости товаров в корзине;
`countBinProducts(): number` - получить количество товаров в корзине;
`checkProductInBin(id: string): boolean` - проверить, есть ли определенный товар в корзине или нет;



#### Класс "Данные покупателя" - CustomerData
Отвечает за хранение данных клиента, выбор вариантов оплаты и проверку этих данных.
Поля класса:  
- `_payment: TPayment` — поле, в котором фиксируется вариант оплаты;
- `_address: string` — поле, в котором фиксируется адрес покупателя;
- `_email: string` — поле, в котором фиксируется электронная почта покупателя;
- `_phone: string` — поле, в котором фиксируется телефон покупателя;

Методы класса:
`setCustomerData(data: Partial<ICustomer>): void` - получение объекта данных покупателя и сохранение их в моджель полностью или частично;
`getCustomerData(): ICustomer` - получение объекта данных покупателя;
`clearCustomerData(): void` — очищает все поля покупателя.
`validateCustomerData(): FormErrors` - проверка поля данных покупателя. если ошибка - возвращает текст ошибки по каждому полю;

## Слой представления (View)

Все классы этого слоя отвечают за отображение интерфейса на странице, поиск HTML-элементов и обработку кликов. 
Они **ничего не знают про сервер и про то, как устроены модели данных**. Они просто берут готовый объект с данными, раскидывают его по инпутам/текстам и выводят пользователю.

Все компоненты этого слоя наследуются от базового класса `Component`, который управляет DOM-элементами.

### Базовые компоненты инфраструктуры:
* **Класс `Modal`** — универсальная «коробка» для модальных окон. Находит крестик закрытия и оверлей. Умеет сама открываться/закрываться и очищать контент, чтобы не захламлять память. Защищена от закрытия при случайном клике по центру окна (`stopPropagation`).
* **Класс `Gallery`** — сетка для каталога на главной. Просто принимает массив уже готовых сверстанных карточек и раскладывает их на экране.

### Семейство карточек товара (Наследуются от абстрактного класса `Card`):
* **Абстрактный класс `Card`** — общая база для всех карточек. Находит и умеет отрисовывать только два общих поля: название товара и его цену (учитывает цену `null` как "Бесценно").
* **Класс `CardCatalog`** — карточка товара для главной страницы. Дополнительно находит картинку и тег категории. Ловит клик по всей карточке через переданный колбэк (`actions`).
* **Класс `CardPreview`** — карточка детального просмотра в модалке. Находит описание товара и кнопку «Купить/Удалить». Если у товара нет цены — сама блокирует кнопку и пишет «Недоступно».
* **Класс `CardBasket`** — карточка товара внутри корзины. Вместо картинок находит и выводит порядковый номер (индекс) строки и кнопку удаления (иконку-корзинку).
* **Динамическое переключение цветов категорий (`CardCatalog` и `CardPreview`)**:
  Внутри сеттера `category` реализована автоматическая покраска фона тега. Класс не использует громоздкие `if/else`, а с помощью цикла перебирает карту констант `categoryMap` и через метод `classList.toggle` динамически навешивает нужный CSS-класс модификатора (например, `card__category_soft`), соответствующий пришедшему с бэкенда тексту.


### Семейство форм (Наследуются от базового класса `Form`):
* **Базовый класс `Form`** — общая база для всех форм. Отвечает за блокировку кнопки отправки, если форма невалидна, и вывод текста ошибок. Самое главное — он через событие `input` автоматически следит за каждым инпутом и сообщает в презентер, какое именно поле изменилось.
* **Класс `FormOrder`** — форма первого шага заказа. Находит инпут адреса и две кнопки выбора оплаты ("Картой" / "Наличными"). Умеет красиво переключать класс активности кнопок через `classList`.
* **Класс `FormContacts`** — форма второго шага заказа. Самая простая — находит и обновляет только два текстовых инпута: email и телефон.


### Изменения в моделях данных (Спринт 2):
Все модели данных теперь принимают в конструктор брокер событий `events: IEvents`. Они полностью изолированы от отображения, но при любом изменении своих полей автоматически уведомляют приложение через генерацию событий в EventBus.

* **Класс `CatalogMain`**: 
  - Метод `saveProducts` после сохранения данных генерирует событие `items:changed`.
  - Метод `setPreview` генерирует событие `preview:changed`.
* **Класс `BinData`**: 
  - Методы `addProduct`, `deleteProduct` и `clearBin` при любом изменении состава корзины генерируют единое событие `basket:changed`. Геттеры стоимости и количества при этом остаются "тихими" и события не эмитят, чтобы избежать бесконечных циклов.
* **Класс `CustomerData`**: 
  - Метод `setCustomerData` анализирует пришедшие частичные данные, обновляет поля и в самом коде (в самом конце метода) генерирует одно общее событие `customer:changed`.
  - Метод `clearCustomerData` сбрасывает все поля и также генерирует событие `customer:changed`.

### Слой коммуникации

#### Класс "AppApi"
Обеспечивает взаимодействие приложения с сервером. Использует композицию и методы базового класса `Api` для отправки и получения данных.

Конструктор:
- `constructor(api: IApi)` — принимает экземпляр базового класса API c интерфейсом `IApi`;

Поля класса:
- `_api: IApi` — объект для выполнения HTTP-запросов;

Методы класса:
`getProducts(): Promise<IProductList>` — выполняет GET запрос на `/product/`, возвращая объект со списком товаров и их общим количеством;
`createOrder(order: IOrder): Promise<IOrderResult>` — выполняет POST-запрос на эндпоинт `/order/`, отправляя данные заказа, и возвращает объект с ID заказа и итоговой суммой для подтверждения покупки;


## Описание работы и учебные задачи

В рамках этой части проекта я выполнял роль разработчика, строящего бизнес-логику для будущего интернет-магазина. 

### Какие задачи я решил:
1. **Спроектировал структуру данных:** Разобрал техническое задание и выделил основные сущности магазина — сам Товар, Корзину для покупок и Личные данные покупателя.
2. **Создал строгие правила (Типизацию):** С помощью TypeScript описал интерфейсы для всех сущностей, что позволяет защитить код от случайных ошибок (например если сервер пришлет пустую цену или вместо текста придет число).
3. **Написал независимые Модели данных:** Создал три класса-модели (`CatalogMain`, `BinData`, `CustomerData`). Они умеют хранить данные, считать сумму корзины, удалять/добавлять товары и проверять, правильно ли покупатель заполнил формы оформления заказа. Эти классы полностью изолированы — они ничего не знают про верстку и кнопки на экране.
4. **Настроил связь с сервером (Слой коммуникации):** Написал класс `AppApi`, который умеет запрашивать реальный список товаров с сервера и отправлять готовый заказ обратно.
5. **Провел тестирование:** В главном файле `main.ts` симулировал работу приложения — проверил каждый метод созданных классов через консоль браузера и успешно связал модель каталога с настоящими данными, пришедшими по сети.
